## 01. 셀프호스팅 에디터는 “파일 존재”와 “사용 가능”이 다릅니다

**관찰**: TinyMCE 파일을 로드하지 못한 상황을 검증하려고 로컬 스크립트를 빈 응답으로 대체했습니다. 대체 에디터 자체는 정상 동작했지만, React 래퍼가 전역 TinyMCE 부재를 감지하면서 `tinymce should have been loaded into global scope` 오류를 출력했습니다. 그 결과 첫 P4a 누적 검증은 25/26 통과였고 콘솔 오류 0 조건을 충족하지 못했습니다.

**현재 해결**: React 에디터를 마운트하기 전에 로컬 스크립트 로드와 전역 객체 존재를 확인합니다. 8초 제한 또는 실패 시 대체 에디터를 렌더합니다. 수정 후 실제 iframe 입력과 대체 편집기 입력을 포함해 28/28 통과했습니다.

**제안**: Harness B3에 다음을 추가하면 좋습니다.

> 스크립트 로드 성공과 에디터 초기화 성공을 구분한다. 전역 객체를 확인한 뒤 React 래퍼를 마운트하며, 라이브러리의 오류 로그를 억제하는 방식으로 콘솔 게이트를 통과시키지 않는다. 동일 페이지의 복수 에디터는 로더 Promise를 공유한다.

**검증 근거**: `officequest/tests/e2e/03-quest-create.spec.ts`의 정상 TinyMCE·대체 에디터 테스트. 현재의 고정 버전 조합은 변경하지 않았습니다.

## 02. 첨부파일 명세에 비동기 취소와 고유 ID가 필요합니다

**관찰 A — 구현 버그**: 파일 ID를 고정 시각과 선택 목록의 인덱스로 만들면, 파일을 두 번 나눠 업로드했을 때 같은 ID가 생성됩니다. React 키가 중복되고 하나를 삭제하면 다른 파일도 함께 삭제될 수 있습니다.

**관찰 B — 구현 버그**: 요청 파일을 SharePoint 링크로 변환하는 600ms 동안 유형을 문의로 바꾸면, 이전 타이머가 뒤늦게 SharePoint 첨부를 문의 폼에 다시 추가할 수 있습니다. 도메인 검증이 잘못된 등록을 막지만 사용자는 이해하기 어려운 실패를 경험합니다.

**현재 해결**: 컴포넌트 식별자와 증가하는 일련번호로 ID를 만들고, 유형 변경·언마운트 때 비동기 작업의 세대 토큰을 무효화했습니다. 타이머뿐 아니라 이미지 FileReader 결과도 같은 원칙으로 처리합니다. 두 상황을 브라우저 회귀 테스트로 추가해 통과했습니다.

**제안**: PRD D22 또는 AC-8.4.3에 다음을 추가하면 좋습니다.

> 첨부 변환 중 퀘스트 유형을 변경하면 이전 유형의 진행 중 작업은 취소되거나 결과가 무시된다. 동일 파일의 반복 선택을 포함해 첨부 ID는 고유해야 하며, 삭제는 선택한 첨부 하나에만 적용된다. 고정 시각에서도 동일하게 동작한다.

문서가 기존 구현 버그의 원인이라는 뜻은 아닙니다. 자동 구현에서 반복되기 쉬운 경계를 명시하자는 의견입니다.

## 03. 단계별 게이트와 AC의 의존 관계를 더 직접적으로 표현하면 좋습니다

**관찰**: P4a에는 게시판과 조회수 검증이 포함되지만, 게시판 행 클릭 후 상세 진입·조회수 증가를 완전히 확인하려면 P4b의 상세 라우트가 필요합니다. 앞 단계에 빈 상세 화면을 만들면 단계 완료의 의미가 흐려집니다.

**현재 해결**: Harness B23의 후속 단계 의존 처리 원칙에 따라 필터·URL·정렬·등록은 P4a에서 검증하고, AC-8.6.3의 상세 진입·조회수 검사는 P4b 태그로 배정했습니다. 테스트를 삭제하거나 기대값을 낮추지 않았습니다.

**제안**: Phase 표에 `이번 단계에서 완료하는 AC / 다음 단계 의존 AC / 최종 재검증 단계`를 한 열씩 추가하면 좋습니다. 특히 라우트 이동, 공용 Teams, 운영자 배너처럼 단계 경계를 넘는 기능에 유용합니다.

## 04. 반응형 화면은 “고정 수치”와 “축소 가능 수치”를 구분해야 합니다

**관찰**: PRD D6의 aside 400px와 264px 사이드바를 함께 유지하면 1440px 화면에서 작성 본문이 상당히 좁아집니다. 초기 구현에서 aside를 320px로 줄였으나, 리뷰에서 명세 차이로 지적되어 현재 400px를 유지하고 더 좁은 구간에서 적층합니다. 유형 설명을 통째로 숨기는 방식도 처음에는 사용했으나 제거했습니다.

**현재 해결**: 문의·요청 설명은 좁은 화면에서도 줄바꿈해 보존하고, 1920px에서는 제목·분야·마감일을 한 줄에 배치했습니다. 실제 뷰포트 검증과 refs 비교를 병행합니다.

**제안**: DESIGN에 1920 / 1440 / 1200 / 모바일 기준으로 `GNB 배치, 사이드바 폭, aside 폭, 본문 최소 폭, 적층 여부`를 표로 제시하면 좋습니다. 정보가 있는 설명·비활성 사유는 유지하고, 장식만 줄일 수 있다는 규칙도 명시하면 해석 차이가 줄어듭니다.

## 05. 저잔액 계정의 현상금 슬라이더 눈금이 모호합니다

**관찰**: AC-8.4.4에 따라 이퀘스트의 현상금 최대값은 300P로 낮아집니다. 그런데 눈금을 항상 0/250/500/750/1,000으로 표시하면 중앙의 실제 값 150P가 500 눈금 위치에 놓입니다.

**현재 해결**: 슬라이더의 실제 최대값에 맞춰 눈금도 계산합니다. 김효성의 1,500P 계정은 원래의 0–1,000 눈금을 그대로 표시합니다.

**제안**: PRD에 다음 중 하나를 명시하면 좋습니다. 현재 구현은 첫 번째 방식입니다.

- 범위를 보유 포인트까지 줄이고 눈금도 같은 범위로 재계산한다.
- 시각 범위는 항상 0–1,000으로 유지하되 초과 구간을 잠금 표시하고 실제 입력을 보유 포인트로 제한한다.

## 06. 설치·브라우저 준비를 기능 구현 전 별도 진단으로 묶으면 좋습니다

**관찰**: 정확히 고정한 패키지 버전 설치 중 캐시된 메타데이터로 ERESOLVE/ETARGET가 발생했습니다. `npm install --prefer-online`으로 고정 버전을 바꾸지 않고 해결했습니다. Playwright 번들 브라우저 다운로드는 시간 초과되어 Harness B2에 따라 설치된 Chrome을 사용했습니다.

**현재 해결**: 실제 검증 명령에 `PW_CHANNEL=chrome`을 지정합니다. 버전 핀과 Appendix A 설정은 유지했습니다. TinyMCE의 알려진 audit 경고는 Harness B10의 로컬 시연 범위에 따라 기록하고 유지했습니다.

**제안**: P0 시작 시 Node 버전, 레지스트리 메타데이터, 로컬 브라우저 채널, 폰트·TinyMCE 파일 존재를 한 번에 확인하는 진단 스크립트를 제공하면 좋습니다. 오류별 재시도 횟수와 대체 명령을 결과에 출력하면 반복 설치 시간을 줄일 수 있습니다. audit 경고 처리 기준은 시연용과 실제 배포용으로 구분해 두는 편이 좋습니다.

## 07. 실패 불변성과 “실패 후 자동 취소”를 액션 단위로 분리해 명시하면 좋습니다

**관찰**: PRD §5.1의 실패 시 DB 불변 원칙과 §7.2의 구매 승인 시 잔액 부족이면 요청 취소 규칙을 같은 reducer 액션에서 처리하면 충돌합니다.

**현재 해결**: 승인 reducer는 실패 시 DB를 바꾸지 않고 오류를 반환합니다. Provider가 별도의 유효한 요청 취소 액션을 실행하고 오류 토스트를 보여줍니다. P1 리뷰와 테스트에 근거를 남겼습니다.

**제안**: PRD 상태머신 표에 `원자적 도메인 액션의 결과`와 `오류 후 UI 오케스트레이션`을 분리해 적으면 좋습니다. 이렇게 하면 실패 불변성 테스트와 사용자가 보게 될 최종 상태를 동시에 명확히 할 수 있습니다.

## 08. 공개 범위를 본문뿐 아니라 사이드바·타임라인에도 적용해야 합니다

**관찰 — 구현 버그**: 진행 중 퀘스트를 보는 제3자에게 제출 카드와 첨부는 숨겼지만, 우측 진행 타임라인에 제출 버전·시각·검수 이력이 노출되었습니다. PRD §8.7의 “제출 이력 비공개”를 본문에만 적용한 오류입니다.

**현재 해결**: 진행 중·보완요청에서는 요청자와 작업자만 제출·검수 타임라인을 볼 수 있게 했습니다. 제3자에게는 공개된 등록·채택 상태만 보여줍니다. 완료 퀘스트의 최종 결과는 기존 공개 규칙을 유지합니다. 브라우저 회귀 검사에 추가했고 통과했습니다.

**제안**: 역할별 공개 범위를 `원래 요청 / 결과물 본문 / 결과물 첨부 / 제출 버전 / 제출·검수 시각 / 최종 보상` 열로 나눠 표기하면 좋습니다. 같은 데이터가 본문·aside·알림·피드에 반복 표시될 때도 동일하게 적용한다는 원칙을 추가하면 누락을 줄일 수 있습니다.

## 09. 진행 단계가 바뀌면 정보의 우선순위도 달라집니다

**관찰**: 등록 시의 요청 본문 전체, 7단계 스테퍼, 작업자, 제출물, 검수 버튼을 한 화면에 순서대로 쌓으면 제출물·승인 버튼이 아래로 밀립니다. ref07은 진행 중 화면에서 채택된 작업자와 제출물을 바로 보여줍니다. 반면 공통 본문 요구만 순서대로 구현하면 ref06 모집 화면의 구성이 그대로 남기 쉽습니다.

**현재 해결**: 진행 중에는 원래 요청을 펼칠 수 있는 접힌 영역으로 보존하고 스테퍼를 압축합니다. 현재 작업물과 검수 행동의 우선순위를 높입니다. 화면 캡처에서 실제 배치를 검증합니다. 최종 이미지 감리에서는 중복 보상 카드가 타임라인을 아래로 밀어 고정 Teams 창에 가리는 문제도 확인했습니다. DESIGN ref07에 맞춰 진행 중·보완요청에서는 보상 카드를 생략하고 진행 로그를 aside 맨 위에 배치했습니다. Teams 창과 타임라인이 겹치지 않음을 별도 DOM 단언으로 검증했고, 재촬영 구도 검토도 통과했습니다.

**제안**: PRD §8.7에 상태별 화면 순서와 접기 기본값을 명시하면 좋습니다. 예: 모집 중은 요청 본문·지원자 중심, 검수 대기는 채택 작업자·최신 제출·검수 중심. SHOULD 스테퍼를 추가할 때 기존 핵심 CTA의 첫 화면 노출을 유지한다는 기준도 도움이 됩니다.

## 10. 권한 표에 보조 행동도 포함하면 누락을 줄일 수 있습니다

**관찰 — 구현 버그**: 물품 상세에서 구매는 운영자에게 제한했지만, 판매자와 Teams 대화 버튼은 판매자가 아니면 누구에게나 보였습니다. 운영자도 버튼을 누를 수 있어 대화 생성 가드가 오류를 던졌습니다. 주 행동만 제한하고 보조 행동을 놓친 사례입니다.

**현재 해결**: 플레이어에게만 거래 대화 버튼을 표시하고 운영자 좋아요도 가드에 맞춰 비활성화했습니다. 공용 대화 생성 API에서도 오류를 잡아 안내하므로 호출자가 가드를 놓쳐도 처리되지 않은 오류가 발생하지 않습니다.

**제안**: 역할별 권한 표를 등록·구매뿐 아니라 좋아요·Teams·편집·사진 조작·공유 같은 보조 행동까지 확장하면 좋습니다. 버튼 표시/활성 규칙과 도메인 가드를 함께 검사하는 항목이 있으면 자동 구현의 누락을 줄일 수 있습니다.

## 11. 알림과 오류 토스트의 표시 우선순위가 필요합니다

**관찰 — 코드 리뷰에서 확인한 충돌 경로**: 구매 승인 때 잔액이 부족하면 별도 액션으로 요청을 취소하고 오류 토스트를 표시합니다. 그런데 취소 액션의 새 알림을 감지하는 effect가 이후 일반 정보 토스트를 띄우면 잔액 부족 이유가 덮일 수 있습니다. 두 개별 기능이 맞게 동작해도 최종 안내가 부정확해질 수 있습니다.

**현재 해결**: 오류 토스트가 표시되는 4초 동안 자동 정보 알림이 덮어쓰지 못하게 했습니다. 시나리오 초기화 때 알림 전달 ID 캐시도 함께 비웁니다.

**제안**: PRD에 `사용자 액션 실패 > 자동 정보 알림` 우선순위 또는 토스트 큐 규칙을 추가하면 좋습니다. 승인 실패·자동 취소·양측 알림처럼 하나의 업무 흐름에서 여러 메시지가 생길 때 최종 사용자가 봐야 할 이유를 수용 기준으로 지정하면 명확합니다.

## 12. 원본 CSS와 Tailwind를 함께 쓸 때 충돌 규칙이 필요합니다

**관찰 — 구현 통합 문제**: 원본의 `ring` 클래스가 Tailwind 유틸리티와 충돌해 진행 링 주변에 의도하지 않은 파란 사각형이 나타났습니다. 또 Preflight 뒤에 적용되는 기본 제목 규칙 때문에 전역 제목 굵기 선언이 무효화되어, 페이지 제목을 고친 뒤에도 Portal 모달 제목에는 같은 문제가 남았습니다.

**현재 해결**: 진행 링을 `progress-ring`으로 바꾸고, 페이지 제목과 모달 제목에 컴포넌트 범위의 굵기 규칙을 적용했습니다. 실제 캡처에서 확인했습니다.

**제안**: Harness에 원본 CSS 포팅 시 클래스 충돌 검사와 스타일 레이어 원칙을 짧게 추가하면 좋습니다. 앱 전용 접두사 사용, Tailwind 기본화 뒤 컴포넌트 규칙 배치, Portal에서도 적용되는 모달 타이포그래피 확인을 권장합니다. DESIGN 토큰의 존재와 실제 계산 스타일의 일치를 별개로 검증하는 현재 Visual 방식은 유지할 가치가 있습니다.

## 13. 운영 지표는 집계 대상 상태를 명시하면 좋습니다

**관찰 — 명세의 선택 여지**: 운영자 헤더는 “열린 플래그 n · high n · 활성 제재 n”을 요구하지만 high가 열린 플래그만을 뜻하는지, 처리된 사례까지 포함하는지 명시하지 않습니다. 두 구현 모두 초기 시드에서는 high 2건이라 첫 화면 검사만으로 구분되지 않습니다.

**현재 선택**: 최근 14일에 탐지되는 전체 high 사례 수와 별도의 열린 플래그 수를 표시합니다. 처리 후에도 근거가 기간 안에 남으면 전체 high 수는 유지됩니다.

**제안**: 라벨을 “전체 high” 또는 “열린 high”로 명확히 하고, high 플래그를 무혐의·조치 처리한 뒤의 기대 집계값도 수용 기준에 추가하면 좋습니다. 시드 값만 맞는 구현을 걸러내는 데 도움이 됩니다.

## 14. 핵심 조치의 가시성은 자동 클릭 성공과 별개입니다

**관찰 — 레이아웃 문제**: 1440px에서 사이드바와 카드 여백을 제외한 운영자 표 영역은 약 1062px인데, 표 최소 폭은 1140px이었습니다. 오른쪽 제재·무혐의 처리 열 일부가 첫 화면에서 가려졌습니다. Playwright는 클릭 전에 자동 스크롤하므로 “버튼 클릭 성공”만으로는 이 문제를 잡기 어렵습니다.

**현재 해결**: 조치 열을 오른쪽에 고정해 근거 열을 가로 스크롤할 때도 버튼이 보이게 했습니다. 기능 테스트에 초기 버튼 위치 검사도 추가했고 통과했습니다.

**제안**: 표·조직도처럼 중요한 조치가 끝 열에 있는 화면에는 “기본 데스크톱 폭에서 핵심 CTA가 추가 스크롤 없이 보인다”는 기준을 넣으면 좋습니다. 클릭 가능 여부와 최초 가시성 검사를 분리하는 방식이 유용합니다.

## 15. 성능 측정용 시계와 업무 시뮬레이션용 시계를 분리하면 좋습니다

**관찰 — 테스트 하네스 문제**: P6에서 하이드레이션 시간을 Navigation Timing으로 측정할 때, 고정 시각을 설치하는 공통 테스트 fixture에서는 `performance.getEntriesByType('navigation')`가 빈 배열이었습니다. 측정 코드가 실패해 실제 화면의 성능과 무관하게 검증이 중단됐습니다. 초기 스켈레톤 검증에서 보류한 스크립트 요청을 해제하는 순서도 라우트 정리와 경합했습니다.

**현재 해결**: 하이드레이션 성능 검사만 고정 시각 fixture 대신 네이티브 브라우저 시계를 사용합니다. 업무 시각·타이머·만료 검사는 기존 고정 시각을 유지합니다. 보류 요청은 해제 후 `unrouteAll({ behavior: 'wait' })`로 종료를 기다립니다. 실제 측정값은 `officequest/qa/performance/dashboard-hydration.json`에 보존합니다.

**제안**: Harness에서 테스트를 `업무 시각 고정 / 경과 시간 측정 / 네이티브 Navigation Timing` 세 방식으로 구분하고, 각 방식의 fixture 예제를 제공하면 좋습니다. “1초 이내” 같은 SHOULD 항목은 측정 시작점·종료점·시계·빌드 모드를 함께 기록하면 다음 자동 구현 결과와 비교하기 쉽습니다.

## PRD 보완에 활용하는 방법

위 의견은 실제 구현·리뷰·회귀 검사에서 확인한 사례입니다. 다음 PRD에서는 각 제안에 기대 동작과 반례를 함께 추가하고, 해당 AC와 단계별 테스트를 연결하는 방식으로 반영하면 좋습니다. 현재 구현의 해결책을 유일한 정답으로 고정하기보다, 반드시 지켜야 할 결과와 선택 가능한 구현 방법을 구분하는 것을 권장합니다.


## 16. 판매자 지정과 구매자 수령 확인을 별도 상태로 나눠야 합니다

**사용자 피드백**: 마켓 목록의 샀어요·구매 요청 버튼을 없애고, 상세에서 판매자가 지정한 최종 구매자만 샀어요로 거래를 완료하도록 변경합니다. 구매 요청 문구도 제거합니다.

**이전 명세의 문제**: 누구나 구매를 요청하고 판매자가 승인하는 경로와, 판매자가 조직도에서 구매자를 선택하면 즉시 정산하는 경로가 함께 있었습니다. “최종 구매자 지정”이 상대의 수령 확인 없이 포인트 이동까지 실행해 행동의 의미가 과했습니다.

**현재 보완**: 목록에는 사진·제목·가격·좋아요·판매자만 둡니다. 조직도에서 예약자와 최종 구매자를 따로 지정하며, 최종 지정만으로는 정산하지 않습니다. 최종 구매자에게만 상세의 샀어요 버튼이 나타납니다. 이 버튼을 눌렀을 때 거래완료와 양측 원장을 한 번에 기록합니다. 단순 예약자는 수령 확인 권한을 갖지 않습니다. NPC 자동 승인도 제거했습니다.

**PRD·Harness 반영 제안**: `거래가능 → 예약 → 최종 구매자 지정(수령 대기) → 구매자 수령 확인 → 거래완료` 표를 추가하고, 각 전환의 실행자·포인트 변경 시점·버튼 노출 위치를 적으면 좋습니다. 기존 경로 A/B/B'와 NPC 자동 승인 테스트는 새 흐름으로 교체해야 합니다. 최종 지정 필드와 완료 후 구매자 필드를 분리하면 단순 예약과 수령 권한이 섞이지 않습니다.

## 17. 실수 취소는 상태뿐 아니라 정산·원장도 되돌려야 합니다

**사용자 피드백**: 샀어요를 다시 누르면 원래대로 돌아가야 합니다.

**현재 보완**: 직접 완료한 구매자는 같은 버튼을 다시 눌러 완료를 취소할 수 있습니다. 최종 구매자 지정은 유지하고 수령 확인 대기 상태로 돌아갑니다. 구매자 환불·판매자 정산 취소를 원자적으로 처리합니다. 기존 원장을 삭제하지 않고 취소 시각과 역분개 원장을 남깁니다. 연속 클릭·새로고침에도 중복 환불이 발생하지 않습니다. 취소된 구매는 반복 거래 탐지에서 제외합니다. 예전 시드 거래에는 새 완료 영수증이 없으므로 임의 환불을 만들지 않습니다.

**남은 정책 결정**: 판매자가 받은 포인트를 이미 사용했다면 단순 역정산은 음수 잔액을 만들 수 있습니다. 현재는 이 경우 원래 상태를 보존하고 취소 불가 이유를 표시합니다. 언제든 무조건 취소를 보장하려면 일정 시간 정산금 잠금, 취소 가능 시간, 운영자 환불 중 하나가 명세에 필요합니다. 즉시 실수 취소는 정상 복원합니다.

**PRD·Harness 반영 제안**: 취소 권한·기간·제재 중 환불 허용 여부·재완료·포인트 사용 후 처리·감사와 모니터링 집계까지 하나의 정책으로 정의하면 좋습니다. 잔액·물품 상태·최종 구매자·양측 원장을 함께 확인하는 회귀가 필요합니다.

## 18. 문의와 요청은 같은 지원·채택 워크플로가 아닙니다

**사용자 피드백**: 문의는 지원하기 없이 댓글형 답변을 바로 쓰고, 질문자가 좋은 답변을 채택합니다. 에디터는 사전에 잠그지 않습니다.

**이전 명세의 문제**: 두 유형의 첨부만 구분하고 지원자 → 작업자 채택 → 결과물 검수라는 상태머신을 공유했습니다. 간단한 질문도 답변 전에 채택이 필요해 설명과 실제 행동이 어긋났습니다.

**현재 보완**: 문의 전용 상세를 분리했습니다. 여러 직원이 공개 답변과 스크린샷을 바로 등록하고, 질문자가 답변 하나를 별점과 함께 채택하면 완료됩니다. 답변 작성은 지원이나 별도 서약 모달을 요구하지 않습니다. 채택 시 기존 현상금·기본 보상·별점 EXP·일일 완료 한도·평가 원장·일일 미션을 함께 반영합니다. 질문자는 자기 문의에 답변하거나 자기 답변을 채택할 수 없고 운영자는 읽기만 합니다. 완료 후에는 추가 답변과 중복 채택을 막습니다. 요청의 기존 지원·채택·반려·재제출 흐름은 유지합니다.

**PRD·Harness 반영 제안**: 문의용 `답변 접수 중 → 답변 하나 채택 → 완료`와 요청용 상태머신을 분리하면 좋습니다. 답변 공개 범위, 수정·삭제·정렬, 복수 답변, 일일 보상 한도에 도달한 직원의 작성 가능 여부, 채택 취소, 보안서약 적용 시점도 명시할 필요가 있습니다. 현재 답변 작성에는 기존 작업 시간·일일 한도 가드를 유지하고, 채택 시 한도를 다시 확인합니다. 게시판의 인원 열은 지원/답변으로 표시하고 내가 참여한 목록에는 답변도 포함합니다.

## 19. 조직도에 동료 포인트를 노출하지 않아야 합니다

**사용자 피드백**: 그룹웨어 조직도에서 직원의 보유 포인트를 보여주지 않습니다.

**현재 보완**: 직원 행의 보유 포인트와 구매 가능 포인트 필터를 제거했습니다. 포인트 부족에 따른 조직도 버튼 비활성도 없앴습니다. 금액을 숨기더라도 이런 필터·비활성 이유가 동료 잔액의 상한·하한을 추정하게 만들 수 있기 때문입니다. 운영자 제재에 따른 제한은 유지합니다. 실제 수령 확인 시에는 구매자가 자기 잔액을 확인하고, 부족하면 자기 버튼에서 안내합니다.

**PRD·Harness 반영 제안**: `본인 잔액 / 동료 정보 / 거래금액 / 운영자 근거`의 공개 범위를 구분하고, 값뿐 아니라 필터·활성 상태·툴팁으로 추론 가능한 정보도 검토하면 좋습니다. 조직도 시각 레퍼런스와 “저잔액 직원 버튼 비활성” AC는 개인정보 원칙에 맞게 함께 바꿔야 합니다. 실제 서비스라면 응답 데이터에서도 다른 직원의 잔액을 빼야 합니다. 현재는 로컬 시연용 공용 DB이므로 화면 비노출 범위입니다.

## 20. 포인트와 경험치는 다른 단위로 보여야 합니다

**사용자 피드백**: 작업자 보상 미리보기의 400 P + 100 EXP를 줄바꿈해 표시합니다.

**현재 보완**: 최종 지급 요약을 포인트 한 줄, 경험치 한 줄로 분리하고 서로 다른 차원의 값을 더하는 더하기 기호를 없앴습니다.

**PRD·DESIGN 반영 제안**: 서로 다른 자원의 병렬 표시 규칙을 정하면 좋습니다. 보상 계산의 더하기는 기본 포인트와 현상금 사이에만 사용하고, 포인트와 경험치는 행·아이콘·단위로 구분합니다. 텍스트 포함 검사뿐 아니라 EXP 행이 P 행 아래에 있다는 실제 배치 검사도 추가했습니다.

## 21. 첨부는 퀘스트 유형과 업로드 의도를 함께 구분해야 합니다

**사용자 피드백**: 요청에도 스크린샷 이미지 첨부를 제공하고, 문의에서는 일반 파일 선택 버튼 자체를 없앱니다. 문의의 스크린샷 안내 문구는 유지합니다.

**현재 보완**: 요청은 일반 파일과 스크린샷 두 동작을 제공합니다. 일반 파일은 기존 SharePoint 링크, 스크린샷 버튼으로 올린 이미지는 본문 주변에서 바로 볼 수 있는 미리보기로 저장합니다. 문의는 스크린샷 입력만 렌더합니다. 등록·답변·작업 결과물의 공통 첨부 컴포넌트와 도메인 검증을 함께 바꿨습니다. 유형 전환 중 취소와 고정 시각 ID 고유성은 유지합니다. 실제 캡처에서 기존의 버튼 1개 기준 절대 배치가 새 버튼 2개와 안내 문구를 겹치게 한 문제를 확인해, 넓은 화면에서 두 버튼의 공간을 확보하고 문구·버튼 경계가 겹치지 않는 검사도 추가했습니다.

**PRD·Harness 반영 제안**: `문의 / 요청` × `일반 파일 / 스크린샷` 지원 행렬과 저장·표시 방식을 정의하면 좋습니다. “모든 요청 첨부는 링크”라는 기존 규칙은 이미지 미리보기와 양립하도록 고쳐야 합니다. 비활성 버튼과 아예 없는 버튼은 사용자 경험이 다르므로 부재 검사로 확인합니다.

## 22. 보상 애니메이션과 효과음은 성공한 도메인 전환에 연결해야 합니다

**사용자 피드백**: 일일 퀘스트·퀘스트 완료·거래 완료를 모션 그래픽과 게임의 동전 획득 효과음으로 표현하고 필요한 부분에도 효과음을 추가합니다.

**현재 보완**: 일일 보상에는 픽셀 코인이 퍼지는 보상 패널, 거래 완료에는 같은 계열의 완료 패널, 완료 취소에는 복원 안내 모션을 추가했습니다. 퀘스트 승인과 문의 답변 채택은 기존 1.8초 하이퍼프레임에 완료 사운드를 연결합니다. 등록·채택·제출에는 짧은 성공음, 좋아요에는 가벼운 입력음, Teams 송수신에는 메시지음, 실패에는 경고음을 구분합니다. 성공적으로 저장한 액션에서만 재생하므로 렌더링·새로고침·상태 동기화로 보상을 다시 연출하지 않습니다.

**브라우저 제약과 현재 해결**: Web Audio로 짧은 음계를 합성해 외부 음원 요청을 없앴습니다. 첫 사용자 입력으로 오디오를 열고, 음소거를 저장하며, 백그라운드에서는 재생하지 않습니다. 동시 보이스는 최대16개로 제한하고 끝난 노드를 해제합니다. 모션 감소 설정에서는 날아가는 코인을 숨기되 성공 문구와 보상 정보는 유지합니다. 지원하지 않는 브라우저는 시각 피드백을 유지합니다.

**PRD·Harness 반영 제안**: 이벤트별 모션·소리·타이밍·우선순위 표와 음소거 기본값·볼륨·첫 입력·반복 입력·백그라운드 복귀 정책을 추가하면 좋습니다. 효과음은 버튼 클릭 자체보다 저장 성공에 연결해야 잘못된 성공 신호를 줄일 수 있습니다. 실제 브라우저에서 첫 보상 재생·음소거 유지·빠른 연속 입력·모션 감소를 검증합니다.

## 23. 폰트의 로컬 대체 경로가 있어도 외부 요청 실패는 남습니다

**관찰 — 실제 전체 회귀에서 재현**: 기능 검사 74개 중 거래·사진 등록 관련 2개가 외부 Paperlogy CDN의 `ERR_INTERNET_DISCONNECTED` 콘솔 오류로 실패했습니다. 폰트의 로컬 파일이 있어 화면은 렌더됐지만 CSS가 CDN을 먼저 요청하므로 콘솔 오류와 불필요한 대기가 남았습니다.

**현재 보완**: 이미 포함된 Paperlogy6개 굵기를 로컬 경로에서 직접 불러오고 불필요한 CDN preconnect를 제거했습니다. 원본 토큰의 중복 CDN font-face 선언은 로컬 CSS를 결합하는 작은 PostCSS 플러그인에서 실행 결과물에만 제외합니다. 같은 이름의 로컬 font-face를 덧씌우는 것만으로는 사용하지 않는 원격 face가 남아 폰트 준비 검사도 false가 될 수 있어 선언 중복 자체를 제거했습니다. 원본 토큰 파일의 바이트 동일성은 유지하며, 최종 CSS에는 로컬 font-face6개만 남는 것을 확인했습니다. 버전이나 디자인 토큰, 원본 refs는 바꾸지 않았습니다. 효과음도 로컬 합성을 사용하므로 추가 네트워크 의존성이 없습니다.

**PRD·Harness 반영 제안**: “로컬 폰트가 존재함” 외에 “실행 중 외부 폰트 요청 없음”을 수용 기준으로 두면 시연 장소의 네트워크 때문에 실패하는 일을 줄일 수 있습니다. 앱 리소스의 기본 경로와 실패 시 대체 경로를 명확히 하고 오프라인·연결 중단 상태도 검사하면 좋습니다.

## 24. 마켓은 화면 전체가 아니라 상품 영역을 스크롤해야 합니다

**현재 보완**: 마켓 목록의 프레임을 뷰포트 높이로 제한하고, GNB·마을 메뉴·제목·검색·필터를 고정된 영역으로 둡니다. 상품 그리드와 빈 결과 안내만 별도의 스크롤 영역에 넣었습니다. 영역 끝의 휠이 문서 스크롤로 이어지지 않게 하고, 키보드로 포커스한 뒤 PageDown으로도 탐색할 수 있습니다. 좁은 화면에서는 왼쪽 메뉴를 간단한 상단 마을 메뉴로 배치합니다. 상품 상세·등록·수정에는 이 목록 전용 고정을 적용하지 않습니다.

**PRD·DESIGN·Harness 반영 제안**: 각 화면의 `고정 영역 / 스크롤 영역 / 높이 기준 / 스크롤 끝의 전파 / 작은 화면 배치`를 명시하면 좋습니다. “사이드바 sticky”와 “상품만 스크롤”은 서로 다른 계약입니다. 시드8개가 한 화면에 들어가는 검사만으로는 이 문제를 놓칠 수 있으므로 상품40개로 늘린 상태에서 스크롤 전후 GNB·사이드바·제목·필터의 위치, 문서 scrollY=0, 실제 상품 이동, 키보드·빈 결과·다른 라우트 복원을 확인합니다.

## 25. 시간 만료는 행동 제한과 게시판 접근 제한을 따로 정의해야 합니다

**사용자 피드백**: 참여 시간이 끝나면 업무 퀘스트 게시판을 비활성화하고, 누르면 “오늘 참여 가능한 시간이 모두 지났어요”를 안내합니다. 내가 참여하거나 요청한 퀘스트는 계속 확인합니다.

**기존 명세와의 차이**: PRD §6.6의 “정확히 3개 버튼 비활성”만 따르면 새로운 퀘스트를 계속 둘러볼 수 있습니다. 이번 요청은 게시판 자체의 접근 정책이 추가되므로 단순히 버튼을 더 잠그는 것으로는 충족되지 않습니다.

**현재 보완**: 공통 시간·참여 판정을 추가해 메뉴와 직접 URL을 같은 기준으로 처리합니다. 사이드바 게시판은 비활성 모양으로 표시하지만 클릭·키보드 입력 시 사유를 안내합니다. 전체 게시판에 이미 머물러 있어도 1초 틱에서 잠금 화면으로 전환됩니다. 주 메뉴의 업무 퀘스트 진입은 일일 퀘스트로 연결해 내 퀘스트 메뉴에 접근할 수 있습니다. 개인 목록·상세는 요청자, 지원자, 채택 작업자, 문의 답변자를 포함합니다. 완료 내역도 본인 관련 건만 유지하고 운영자는 기존 열람 권한을 유지합니다. 새 참여·제출의 기존 시간 가드는 유지하며, 본인 퀘스트의 검수와 마을 거래는 계속 가능합니다. KST 날짜 변경·타이머 복구 때 다시 열립니다.

**PRD·Harness 반영 제안**: `메뉴 상태 / 목록 범위 / 상세 권한 / 쓰기 동작 / 운영자 예외 / 초기화` 행렬을 추가하면 좋습니다. “참여”에는 댓글형 문의 답변과 채택 작업자도 명시해야 합니다. 내 목록 쿼리 문자열을 붙였다는 사실 자체가 전체 열람 권한이 되지 않도록 실제 결과를 본인 관계로 필터링하고, 무관한 상세 주소에서는 조회수도 증가시키지 않습니다. 시연 타이머와 실제 일일 참여시간 정책의 차이도 명확히 해야 합니다. 실제 서비스의 접근 제한은 서버에서도 검증해야 하며 현재는 로컬 시연 앱 범위입니다.

## 26. 티어 안내와 코스튬은 성장 상태와 외형 선택을 구분해야 합니다

**사용자 피드백**: 스테이터스 옆 i 아이콘에서 남녀 캐릭터의 레벨·티어별 변화를 안내하고, 대시보드 캐릭터를 눌러 헤어와 의상을 고릅니다. 의상은 레벨에 따라 해금합니다.

**현재 보완**: 기존 수식(100 EXP당 1레벨)과 6티어 경계(Lv.1·5·10·15·20·25)를 그대로 사용합니다. 안내는 남녀 전환과 6단계 외형·EXP 구간을 제공합니다. 꾸미기는 남녀 외형, 헤어 2종과 의상 6종이며 장비·망토·날개는 의상 한 파트에 포함합니다. 해금 전 의상은 미리 볼 수 있지만 선택할 수 없고, 도메인 저장 가드에서도 레벨을 재확인합니다. 저장 전 미리보기·취소를 지원하며 사용자별 외형을 공용 DB에 저장해 새로고침과 기존 동기화에 반영합니다. 외형은 능력·포인트·보상에 영향을 주지 않습니다.

**현재 결정 및 명세 보완 제안**: 기본은 현재 티어 자동 장착이며 해금된 하위 의상도 자유롭게 고릅니다. 선택 의상과 실제 성장 티어를 분리하므로 골드 사용자가 실버 의상을 입어도 티어 배지·오라는 골드입니다. 시즌 초기화 시 헤어와 의상 선호는 유지하고, 잠긴 의상 대신 현재 티어 의상을 표시합니다. 같은 레벨을 다시 달성하면 선호 의상이 돌아옵니다. PRD에는 의상 목록·해금표·초기 외형·성별 선택·시즌 초기화·보상 무관성·저장 범위를 함께 정의하면 좋습니다. 기존 저장 데이터에는 선택 필드가 없으므로 기본 외형으로 호환합니다. 이번 구현의 헤어 수는 성별당 2종이며 추후 추가할 수 있습니다.

## 27. 생성형 캐릭터 자산은 조합별 일관성과 생성 이력이 필요합니다

**사용한 경로**: i 아이콘은 기본 내장 imagegen으로 투명 PNG를 생성했습니다. 캐릭터는 사용자가 GPT 제공자와 이미지 생성 이용 가능 여부를 확인한 뒤 sprite-gen의 GPT 이미지 행 파이프라인으로 생성합니다. 별도 API 키나 유료 API 경로로 전환하지 않습니다. 제공자 선택 확인은 스킬의 필수 단계이며, 앱의 일반 사용 흐름에는 포함하지 않습니다.

**설계 결정**: 헤어를 옷 위에 임의로 붙이면 목·어깨·긴 머리·망토·날개의 겹침이 어색해질 수 있습니다. 사용자에게는 헤어/의상 두 파트만 제공하되, 2성별 × 2헤어 × 6의상 조합을 완성된 전신 자산으로 준비해 부위 연결을 보존합니다. 티어별 날개·검 등은 의상에 포함하고 별도 파츠를 추가하지 않습니다. 원격 이미지 의존성 없이 앱에 최종 자산을 포함합니다.

**병목과 제안**: 기존 Harness는 코드 픽셀 행렬만 허용하지만 이번 요청은 생성형 스프라이트를 명시했습니다. 작업자가 원본 토큰·refs를 바꾸기보다 앱 자산 경로와 생성 이력·조합표·실제 검증 기록을 추가하는 예외가 필요합니다. 생성 도구의 기본 행 프롬프트는 동작/정체성 고정 중심이어서 의상 변형의 의도를 별도로 명시해야 합니다. 이미지의 개수만 맞추는 검사는 부족하며 투명 배경, 완전한 전신, 동일한 바닥선·크기, 헤어 식별, 의상 순서와 작은 화면의 가독성을 직접 확인해야 합니다. 코스튬 수가 늘면 조합 수가 곱해지므로 자산 예산과 승인 기준도 명세에 포함하면 좋습니다.


### 27-1. “도트 스타일”만으로는 기존 아바타 스타일이 고정되지 않습니다

**실제 사용자 검토에서 발견한 문제**: 첫 생성 결과는 128px 셀의 세밀한 치비 캐릭터였습니다. 픽셀처럼 보이는 윤곽과 정상 추출·투명도 검사만으로는 원본의 큰 사각 픽셀·단순한 눈·짧은 몸 비율을 만족하지 못했습니다. 기능 검사는 통과했지만 사용자가 기존 아바타 스타일과 다르다고 판단했습니다. 생성 파이프라인의 성공과 디자인 적합성은 다른 게이트입니다.

**보완 방향**: 기존 코드의 브론즈 아바타를 실제 픽셀 그대로 래스터화한 기준 이미지를 사용합니다. 새로 그린 기준 인물을 다시 참고하면 최초 스타일 편차가 모든 변형에 전파되므로 원본을 직접 기준으로 고정합니다. 출력은 실제 24×24 PNG와 24×24 캔버스, 정수 배율 확대입니다. 머리/몸 비율·2×2 눈·평면 색·짧은 팔다리·1픽셀 윤곽을 생성 프롬프트와 검증 항목으로 명시하고 남녀·헤어·6티어를 다시 생성합니다. 원본 픽셀 행렬 자체는 변경하지 않습니다.

**PRD·DESIGN·Harness 반영 제안**: “2D 도트” 대신 `기준 자산 / 네이티브 해상도 / 정수 배율 / 머리·몸 비율 / 눈 형태 / 팔레트 / 허용 디테일 / 스타일 검토`를 명시하세요. 자산 생성 전 원본 기준 컷을 사용하고, 자동 품질 검사를 통과했더라도 원본과 나란히 비교하는 디자인 게이트를 두면 불필요한 전체 재생성을 줄일 수 있습니다.


**도구 경계에서 추가로 발견한 병목**: 작은 도트 자산은 색 경계가 반복되어 픽셀 간격 검출이 절반/배수로 추정되는 경고가 발생했습니다. sprite-gen의 기본 컴포넌트 분리도 한 여성 망토 행에서 6개를 분리하지 못했습니다. 임의의 동일 폭 자르기나 직접 픽셀 수정을 쓰지 않고, 도구가 제공하는 `--segmentation projection`과 `pixel_unfake`의 행 공통 간격 복구를 사용했습니다. 최종 추출·검사 오류는 없으며 간격 추정 경고는 지우지 않고 생성 이력에 보존합니다. 24개 파일의 실제 24×24 크기·0/255 알파·서로 다른 출력, 눈·머리·망토·날개는 별도로 확인합니다.

## 28. 시연용 첨부는 실제 사내 서비스 주소를 생성하지 않아야 합니다

**사용자 피드백**: Q3 원본 엑셀 같은 첨부에 실제 SharePoint 링크를 만들지 않고, 클릭하면 “다운로드 중”만 가볍게 표시했다가 페이드아웃합니다.

**기존 문제**: 하네스의 고정 SharePoint URL 조합을 그대로 구현해, 존재하지 않는 사내 사이트를 새 탭으로 여는 링크가 렌더됐습니다. 시연 중 인증·권한·없는 파일 같은 앱 외부 화면으로 벗어납니다. 실제 파일 업로드·저장이 범위 밖인데 화면은 실제 다운로드를 약속하는 모순입니다.

**현재 보완**: 새 첨부는 파일명·크기·식별자만 저장하며 URL을 만들지 않습니다. 기존 저장 데이터의 원본·제출물·답변 첨부 URL도 읽어올 때 제거합니다. 파일명은 외부 앵커 대신 키보드로도 누를 수 있는 버튼입니다. 클릭 시 한 개의 작은 “다운로드 중” 안내가1.4초 안에 페이드아웃하고 실제 네트워크 요청·새 탭·다운로드는 발생하지 않습니다. 연속 클릭은 안내 하나의 시간을 다시 시작하고, 포커스와 거래·퀘스트 상태를 바꾸지 않습니다. 스크린샷 미리보기는 기존 방식으로 유지합니다.

**PRD·Harness 반영 제안**: `시연 / 실제 연동`을 자원별로 명시하고, 시연용 첨부의 계약을 실주소 생성이 아닌 파일명 보존·안내 표시·외부 이동 없음으로 바꿔야 합니다. URL 문자열을 확인하던 테스트도 클릭 후 라우트·팝업·다운로드·외부 요청이 없는지 검사하도록 바꾸면 좋습니다. 실제 다운로드 구현 시에는 별도 저장·권한·오류·만료 정책을 정의합니다.

## 29. 호버 애니메이션의 효과음도 하나의 입력 정책으로 관리해야 합니다

**사용자 피드백**: 상단 메뉴, 중고물품 글 등록, 그룹웨어 조직도의 예약자/최종 구매자 지정에 마우스 오버 효과음을 추가합니다.

**현재 보완**: 상단 주요 메뉴와 운영자 메뉴, 마을 등록 진입·등록 제출, 직원별 예약자·구매자 지정 버튼에 짧고 작은 호버음을 연결합니다. 공통 버튼의 선택 속성으로 켜므로 특정 화면별 복제 코드 없이 비활성 버튼은 소리를 내지 않습니다. 마우스 입력만 처리하고120ms 간격으로 제한해 경계 부근 왕복·빠른 이동의 중첩을 줄입니다. 음소거·백그라운드·동시 보이스16개 제한·종료 노드 정리는 기존 오디오 정책을 따릅니다.

**브라우저 제약 및 PRD·Harness 제안**: 마우스 이동만으로 브라우저의 오디오 잠금을 해제할 수는 없으므로 첫 클릭/키 입력으로 오디오가 열린 뒤 재생합니다. 최초 호버에서 강제로 AudioContext를 열지 않습니다. 모션별 `호버 / 클릭 / 저장 성공` 사운드를 구분하고, 음량·길이·반복 간격·비활성·터치·음소거 정책을 표로 명시하면 좋습니다. 호버는 보상 성공음보다 작고 짧게 설정합니다.

## 30. 문의 답변 작성 횟수와 완료 보상 횟수는 분리해야 합니다

**사용자 피드백**: 참여 시간이 남아 있는 동안 문의 답변 작성 횟수 제한을 없앱니다.

**발견한 제한**: 답변 수 자체의 제한은 없었지만, 오늘 퀘스트 완료 보상2회를 받은 사용자에게 답변 작성도 막는 가드가 있었습니다. 그 결과 업무 퀘스트를 이미 해결한 직원은 알고 있는 문의에도 도움을 줄 수 없었습니다.

**현재 보완**: 문의 답변 작성의 일일 완료 횟수 조건을 제거했습니다. 같은 문의·여러 문의에 답변을 계속 등록할 수 있습니다. 참여 시간, 본인 문의 답변 금지, 답변 본문·이미지 검증, 접수 종료 상태와 운영자 권한은 기존 기준을 사용합니다. 이 변경은 작성 가능 여부에 대한 것이며, 채택 시 지급되는 일일 완료 보상2회 한도는 기존 명세대로 별도 검증합니다.

**PRD·Harness 반영 제안**: `답변 작성 수 / 채택 수 / 보상 지급 수 / 참여 가능 시간`을 각각 정의해야 합니다. 작성과 보상을 같은 카운터로 제한하면 지식 공유를 막을 수 있습니다. 보상 한도에 도달한 답변의 채택 시점·보상 이월/미지급 여부는 별도 정책 결정이 필요합니다. 현재는 보상 한도 검사와 기존 안내를 유지합니다.

### 29-1. 같은 등록 동작의 모든 진입점에 피드백이 연결돼야 합니다

**추가 사용자 피드백**: 퀘스트 등록하기에 마우스 오버 효과음이 빠졌습니다. 이전에는 물품 등록만 공통 버튼의 호버음 속성을 켜서 퀘스트 등록 동작이 누락됐습니다.

**현재 보완**: 사이드바 퀘스트 등록, 게시판 등록하기, 등록 폼의 최종 버튼, 보안서약 모달의 동의 후 등록에 같은 호버음을 연결했습니다. 음소거·비활성·첫 입력·반복 간격 정책은 공통 오디오 구현을 사용합니다. 실제 등록 저장 성공음은 기존 도메인 액션에서 한 번만 재생되며 그대로 유지합니다.

**PRD·Harness 반영 제안**: 개별 화면 버튼 목록만 확인하면 같은 동작의 다른 진입점을 놓칠 수 있습니다. `등록 진입 / 폼 제출 / 서약 확인 / 저장 성공`처럼 사용자 여정별로 소리·모션 대응표를 만들고, 각 진입점의 호버음과 비활성/음소거, 성공음 중복 여부를 함께 검사하면 좋습니다.


## 31. 거래 상태를 바꾸면 자동 대화 문구도 함께 바꿔야 합니다

**사용자 피드백**: 팀즈의 “[샀어요] 눌러주시면 바로 승인할게요”를 구매자 지정 후 수령 확인을 안내하는 표현으로 바꿉니다.

**현재 보완**: 자동 응답을 “구매하시면 최종 구매자로 등록해 드릴게요. 물품을 받으신 뒤 [샀어요]를 눌러 주세요~”로 변경했습니다. 구매자가 샀어요를 누른 뒤 판매자가 추가 승인해야 한다는 잘못된 기대를 없앱니다. 이미 저장된 거래 대화도 정확히 일치하는 예전 자동 응답만 읽을 때 교체합니다. 사용자가 직접 작성한 메시지와 업무 인수인계 대화는 보존합니다. 대화 안내만 바뀌며 실제 구매자 지정·수령 확인은 기존 버튼 동작에서 처리합니다.

**PRD·Harness 반영 제안**: 거래 상태 전환의 영향 범위에 버튼·안내·알림뿐 아니라 자동 대화·시드 메시지·저장된 시연 응답을 포함해야 합니다. 자동 응답이 실제로 하지 않는 승인이나 구매자 지정을 약속하는지, 동일한 거래 순서를 설명하는지 문구 회귀 검사로 확인하면 좋습니다. 실제 서비스의 사용자 대화 이력은 임의로 고치지 않고, 시연의 정확한 자동 응답만 이관 대상으로 구분합니다.
